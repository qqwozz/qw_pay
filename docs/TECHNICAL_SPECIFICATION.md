# Техническое задание (ТЗ) — Платёжная система qw_pay

Детализированное техническое задание для проекта `qw_pay`.

---

## 1. Цели и границы системы

**Цель**:  
Разработать платёжную систему — упрощённый аналог внутренних банковских переводов с поддержкой валютных счетов, антифрод-анализом и микросервисной архитектурой.

**Не входит в MVP**:
- P2P-переводы между разными банками (только внутренние счета);
- платёжные шлюзы / эквайринг;
- мобильное приложение (только веб-интерфейс);
- реальный SWIFT/ISO 20022.

---

## 2. Функциональные требования

### 2.1 Регистрация пользователей
- Регистрация по email / телефону.
- Подтверждение через OTP (для упрощения — код в лог).
- Роли: `USER`, `ADMIN` (админ видит audit log, блокирует счета).

### 2.2 Счета
- У каждого пользователя может быть несколько счетов в разных валютах (`RUB`, `USD`, `EUR`).
- Атрибуты счёта:
  - `id`
  - `user_id`
  - `currency`
  - `balance` (numeric, не float)
  - `status` (ACTIVE / BLOCKED)
  - `version` (для optimistic locking)
  - `created_at`, `updated_at`

### 2.3 Переводы между счетами
- Внутрисистемные переводы (счёт → счёт).
- Поддержка переводов в **разных валютах** (конвертация по курсу, сначала фиксированный курс, позже — внешний API).
- **Идемпотентный ключ** (`idempotency_key`) на стороне клиента — повторная отправка не создаёт новый перевод.
- Проверка перед списанием:
  - счёт существует, не заблокирован;
  - достаточно средств;
  - лимиты: макс. сумма за перевод / день.

### 2.4 История операций
- Просмотр своих переводов (отправленные / полученные).
- Фильтры: дата, валюта, счёт.
- Пагинация.

### 2.5 Валютные счета
- Отдельный микросервис курсов (или заглушка) — внешний REST API.
- Конвертация делается **на момент перевода**, фиксируется в транзакции.

### 2.6 Антифрод-анализ
- Каждый перевод перед проводкой проверяется антифрод-модулем.
- Сценарии подозрений:
  - частые переводы на новый счёт;
  - превышение среднего чека в N раз;
  - переводы в ночное время;
  - совпадение с чёрными списками (адрес, device_id).
- ML-модель (Python) возвращает риск от 0 до 1.
- При риске > порога:
  - перевод блокируется;
  - событие уходит в audit log;
  - пользователь получает уведомление.

## 3. Архитектура (микросервисы)

| Компонент            | Язык     | Задачи |
|----------------------|----------|--------|
| API Gateway          | Go       | маршрутизация, аутентификация (JWT), rate limiting |
| Account Service      | Go       | создание счетов, баланс, optimistic lock, блокировка |
| Transaction Service  | Go       | создание переводов, идемпотентность, ACID |
| Anti‑Fraud (высокий) | C++      | низкая задержка (<5 мс), подсчёт фичей в реальном времени |
| Anti‑Fraud (ML)      | Python   | предсказание риска, обучение, batch-вычисление фичей |
| Currency Service     | Go       | курсы валют (mock или внешний API) |
| Audit Log Service    | Go       | журнал неизменяемых событий |

**Коммуникация**:  
- Синхронно — gRPC (между Go-сервисами) или REST (внешние вызовы).
- Асинхронно — Kafka / RabbitMQ:  
  *перевод создан → антифрод-анализ → подтверждение / отклонение*.

## 4. База данных (PostgreSQL)

### 4.1 Схема (ключевые таблицы)

**users**  
- id (PK), email, phone, role, created_at

**accounts**  
- id (PK)  
- user_id (FK)  
- currency (RUB/USD/EUR)  
- balance (numeric)  
- version (int)  
- status

**transactions**  
- id (PK)  
- idempotency_key (unique)  
- from_account_id  
- to_account_id  
- amount (numeric)  
- currency  
- exchange_rate_used (nullable)  
- status (PENDING / EXECUTED / REJECTED / BLOCKED_BY_FRAUD)  
- created_at

**fraud_checks**  
- transaction_id  
- risk_score  
- verdict (ALLOW / BLOCK)  
- features_json  
- checked_at

**audit_log**  
- id, user_id, action, old_value, new_value, created_at, ip_address

### 4.2 Требования
- **ACID-транзакции** при UPDATE баланса двух счетов.
- **Optimistic locking** через `version` в accounts.
- Индексы: `(user_id, currency)`, `transaction.created_at`, `idempotency_key`.

## 5. Технические решения

### ACID-транзакции
Пример (в Transaction Service):
```sql
BEGIN;
  SELECT balance, version FROM accounts WHERE id = $1 FOR UPDATE;
  UPDATE accounts SET balance = balance - $2, version = version+1 WHERE id = $1 AND version = $3;
  INSERT INTO transactions (...);
COMMIT;
```

### Идемпотентность
- Хранить `idempotency_key` с уникальным индексом.
- Если ключ есть и перевод выполнен — вернуть существующий результат.

### Optimistic locking
- При конкурентных переводах с одного счета обновление `version` не даёт потерять обновления.
- Если версия не совпала → retry на уровне приложения.

### Audit log
- Триггерная или программная запись всех изменений баланса, статуса счёта, блокировок.
- Неизменяемый: логи только `INSERT`.

## 6. Антифрод

### 6.1 C++ engine (real‑time)
- Хранит в памяти скользящие окна агрегаций (суммы, частоты) для каждого пользователя / счёта.
- Обновляет фичи за O(1).
- Передаёт feature vector в Python-модель через протокол (например, shared memory / gRPC).

### 6.2 Python ML-модель
- Лёгкая модель (логистическая регрессия / RandomForest) — <10 мс инференс.
- Обучается на исторических транзакциях и финальных вердиктах (manual review).
- Порог риска настраивается (например, 0.85).

### 6.3 Пример фичей
- кол‑во транзакций за последние 5 минут;
- отношение суммы перевода к среднему чеку пользователя;
- новый ли счёт получателя (< 1 дня);
- device fingerprint (пока заглушка);
- временная аномалия (02:00 – 05:00).

## 9. План реализации (по этапам)

1. **MVP без антифрода**  
   – регистрация, счета, переводы, идемпотентность, optimistic lock.

2. **+ антифрод (C++ + Python)**  
   – асинхронная проверка (через очередь), блокировка переводов.

3. **Валютные переводы и курсы**  
   – конвертация, интеграция с Currency Service.

4. **Audit log + админка**  
   – просмотр логов, ручная блокировка счетов.

5. **K8s деплой**  
   – helm-чарты, мониторинг (Prometheus + Grafana), логи (ELK).
